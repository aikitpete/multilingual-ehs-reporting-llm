Backend — how it works

One photo. One report. Four outcomes.

The worker's own language in, everything a Korean site needs out.

● runs in the demo today  ·  ◌ proposed design

1 · The photo

Worker reports a hazard Photo with the danger spot marked, voice or text, category, severity, location, in their own language, chosen once at setup.
→

2 · AI ◌

Translate and structure Vietnamese, Uzbek or Chinese into formal Korean, returned as JSON against a fixed schema.
→

3 · Output

Korean site report One structured record: summary, location, suggested action, sign key.
Site manager Review, assign an owner, log the corrective action.
Warning sign 🔒 Korean plus the worker's language, printed for the site.
Training card Photo and caption, back into the crew's app.
Government 🔒 Aggregate counts and trends only, no names, no language. restricted by the API, not by hiding a column

The fork is the point. The worker's language and identity never reach the supervisor's table or the government view. The Korean report is generated once and then routed, so no branch can leak what the others were never given.

Example — the translation prompt, and what comes back

EXAMPLE · proposed, not the live call

System

You write Korean construction-site safety reports. Translate the worker's report into plain formal Korean for the safety manager.

Use only facts in the input, never invent a detail, never change the severity, return JSON only.

Output language is fixed by the prompt, so the worker never has to read Korean.

Input — the worker's own words

{
  "lang": "vi",
  "category": "falls",
  "severity": "high",
  "location": "4F east stairwell",
  "note": "Cầu thang tầng 4 có một tấm
  ván bị lỏng, tôi suýt vấp ngã.
  Cần cố định lại ngay."
}

The original is stored unedited and stays the worker's own record, so the translation is never the only version.

Output — JSON, routed to each branch

{
  "summary_ko": "4층 동쪽 계단에 발판이
  느슨하게 놓여 넘어질 위험이
  있습니다. 즉시 고정이 필요합니다.",
  "action_ko": "느슨한 발판을 즉시
  고정하고 주변을 정리하십시오.",
  "signal_word": "위험",
  "hazard_name": "추락",
  "needs_review": false
}

위험 and 추락 come from the app's fixed signage table, not from the model's own wording, so a printed sign always reads like a real sign.

Demo today: the phone posts to a live server and both dashboards update from it, and one real model call runs, the report-quality tip at POST /ai-feedback. The translation pipeline above is the design, not running code. needs_review sends anything unclear to a person before a sign or a translation is used.
