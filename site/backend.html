Backend architecture · how the system would work

How the backend works

One worker speaks a hazard into a phone in Vietnamese; a Korean site manager gets an actionable report, a printable warning sign in two languages, and a training card for the same crew — while the government sees only aggregate numbers. This page is the system behind that, and it separates what the demo actually runs today from what a real deployment would need.

The system at a glance

From a spoken sentence to a printed sign

Six stages. The only one a worker ever sees is the first.

Step 1
Capture Worker holds to speak (or types), picks a photo, marks the danger spot, sets category / severity / location. Language is chosen once, at setup.
Step 2
Ingest API Authenticated, site-scoped write. Media goes to private storage; the structured record goes to the report database. Nothing is generated here, so capture never fails because a model is slow.
Step 3
AI workers (async) Queued jobs: speech → text, translate to Korean, check the worker's severity vs. the category, draft the management report. Failures retry and fall back to a human, never to invented content.
Step 4
Human review A supervisor triages and assigns; the Safety & Health Manager records corrective action. A person approves anything safety-critical before a sign or translation is printed.
Step 5
Outputs Korean management report, bilingual warning labels (fixed signage wording, not the worker's sentence), and a training card fed back into the same app.
Step 6
Aggregate view Government sees counts, categories and trends by site — never an individual report, never the worker's language. Enforced by the API, not by hiding a column.
The 원청 → 하청 (primary contractor → subcontractor) chain is modelled explicitly here, because a worker reporting a hazard usually doesn't know — and the system shouldn't guess — which company is accountable for fixing it.
What runs today vs. what a real backend adds
PieceDemo todayProposed for a real deployment
Report storage An in-memory array in server/server.js. Restarting the process clears every report — fine for a live demo, useless as a record. Relational database of record, one tenant per company and one scope per site, so a supervisor can only ever query the sites they're assigned to.
Photos Stay on the device. The submitted payload carries text fields only — the marked-up image is never uploaded. Private object storage, short-lived signed URLs so an image can't be fetched from a leaked link, and location metadata stripped before storage.
AI One genuine call: POST /ai-feedback asks a model for a single short tip on improving the description, in the worker's language — but only if ANTHROPIC_API_KEY is set server-side. The Korean report, translations, signs and training cards are hand-built demo content. A queued pipeline (transcribe → translate → classify → draft) with retries, a per-request budget, and a review queue. Every generation is stored with the record it produced, so a manager can see what the draft was based on.
Authentication None. The demo server is open, CORS *, reachable by anyone who has the tunnel URL. Identity per person (worker / supervisor / manager / auditor), issued per site, revocable on the day someone leaves a crew. The worker's phone holds no long-lived secret.
Worker's language Sent in the payload and hidden at the dashboard's UI layer — the table shows English only, and the language appears in a click-to-reveal modal. A restricted field enforced server-side: the general report API doesn't return it at all. A UI convention is not access control.
Transport A Cloudflare quick tunnel with a random hostname hardcoded in the app and both dashboards; it changes on every restart and dies with the laptop. A stable HTTPS endpoint with a real certificate, config supplied to the client at build time, and no shared secret living in a client binary.
Dashboards Poll the same open endpoint every few seconds and fall back to seed data when it's unreachable. Read-only APIs per role, paginated, with the aggregate endpoint physically unable to return individual records.
Tests node server/e2e-test.js — 27 checks against a throwaway server on its own port, including that AI feedback never blocks a submit. Same contract tests kept as the safety net, wired into CI, plus tests that a supervisor's token cannot read another site's reports.
The demo column is not aspirational — it describes server/server.js as it exists in this repo. The proposed column is a design, not a commitment to any vendor or price.
The lifecycle of one report

Status is about the work, not the danger

Severity (low / medium / high) is what the worker says about the hazard. Status is where the report is in someone's queue. Keeping them separate is what makes "how many high-severity reports are still untouched?" a question the system can actually answer.

SubmittedProcessingReady for reviewAssignedCorrective action loggedResolved
  • Submitted — the record is already durable and visible to the supervisor, before any AI step runs. Generation is an enhancement on top of a saved report, never a gate in front of one.
  • Processing — transcription, translation and drafting run as jobs. If a job fails or times out, the report falls through to Ready for review with a plain-text description rather than being blocked or auto-approved.
  • Assigned — a named person is accountable, on the correct layer of the 원청/하청 chain.
  • Corrective action logged — the Safety & Health Manager records what was done, matching the investigation duty the governance model assigns to that role. Evidence is additive: the original report is never edited.
  • Resolved — closes the loop, and feeds the aggregate compliance view.
System capability map

The governance model lists seven capabilities the system must provide. These are the same seven, one line each on how the backend would carry them.

Report intake Proposed

Offline-tolerant capture: a report queues on the phone if the site has no signal, then syncs. Photo, marked area, category, severity, location, description. The worker proposes severity and category; a supervisor can correct them.

Triage & assignment Proposed

Rules on high-severity reports so that none sits untouched, an escalation path that works across the subcontracting chain, and a visible owner per report rather than a flat "employer" field.

Label generation Proposed

Signage wording comes from a fixed lookup table — signal word from severity, hazard name from category — rendered in Korean plus the worker's language. Real signs state a hazard; they don't read like an incident report, and the worker's own words stay available for comparison.

Training content Proposed

An approved report becomes a training card (photo, translated caption, short quiz) for the same crew. Human approval gates what gets taught, so a mis-translation never becomes curriculum.

Compliance dashboard Proposed

Site- and company-level aggregates: counts, categories, repeat locations, action times. No individual report content, no worker identity.

Access control & privacy Proposed

Role- and site-scoped authorization at the API. The worker's language is one restricted field, readable only by the Safety & Health Manager in the context of a sign or follow-up material.

Audit trail Proposed

Append-only. Corrections are new entries; the original submission stays intact and attributable, so "what did the worker actually report" always has an answer.

Notifications Proposed

The one capability the governance model doesn't yet list: getting a high-severity report in front of a named person on a crew's phone, and confirming they saw it.

What's deliberately not decided

Retention & deletion Open question

No policy exists yet for how long reports and photos are kept, who may delete them, or on what legal basis. This has to be settled before a real pilot, not after — it changes the schema, not just a settings screen.

Response time Open question

No source sets a required time-to-action on a high-severity report. "Every high-severity report has a named owner" is a defensible product default; it should not be presented as a legal deadline.

Role collapse on small sites Open question

On a small site the supervisor and the Safety & Health Manager may be one person. The access rules must state what happens when the roles merge — the restricted language field becomes much weaker if a single login holds both.

Government access Open question

Aggregate-only is this project's proposal, not a confirmed legal requirement. Any move toward per-report government access needs a specific legal basis and a visible audit entry.

Korean privacy law Open question

Sending a worker's speech, photos and location labels to a hosted model means personal data leaves the site. Korean personal-data law would govern purpose limitation, retention, overseas transfer and the processor contract — a legal question to confirm before building, not a checkbox after.

Where it runs Open question

Korean-region hosting and whatever public-sector certification a government customer requires are both plausible constraints for this buyer, and neither is settled here. Flagged as a consideration for a pilot conversation.

What this page is, and isn't. The only backend code that exists in this repo is server/server.js (an in-memory store for the live demo) and its test server/e2e-test.js. Everything labelled Proposed is a design — no service, vendor, price or certification is committed, and nothing here implies government adoption, a pilot, or measured results. The point of the page is that a reviewer can see which half of the story is built and which half is a plan, in about a minute.
